Part 1 - Quick Start

  1. Confirm that the PC can reach the SIM300 device over the network.
  2. Sign in with POST /auth/login and copy the returned token.
  3. Send later requests with the HTTP header Cookie: access_token=<token>.
  4. Use GET /api/v1/system/info or GET /api/v1/system/monitor/stats to confirm the device is reachable and healthy.
  5. Read current app data before changing anything, for example getModbusRegisters and getIOLinkEndpoints.
  6. For configuration changes, call the related update, create, delete, or reset API.
  7. Call reloadApps after configuration changes so the runtime uses the saved configuration.

A request can take up to one minute when the device is operating under heavy workload. Set the request timeout in your REST client to at least 60 seconds.

Recommended testing tool For manual API testing, install an API client such as Postman on the service PC. Postman makes it easier to set request URLs, JSON bodies, timeouts, and the required Cookie: access_token=... header. For the login request, also set Accept to application/json. cURL and PowerShell are also suitable when command-line testing is preferred.
Do not use these APIs for high-frequency data polling The APIs are intended for remote checks, configuration changes, service updates, and occasional value reads or writes. They are not intended for highly frequent data fetching. Frequent API polling can consume SIM300 processing resources and negatively affect other runtime work, including IO-Link endpoint polling and Modbus register value updates.

Part 2 - Sign In And Use The Token

The SIM300 API requires an access token. First send a login request. Do not put usernames, passwords, or tokens into shared documents, screenshots, or source code. 

POST http://<device-ip>:8080/auth/login
Accept: application/json
Content-Type: application/json

{
  "username": "<username>",
  "password": "<password>",
  "realm": "admin"
}

Use "admin" or "users" for realm, depending on the account type provided by the device administrator.

The login request must include Accept: application/json so the device returns the token as JSON.

Typical login response:

{
  "token": "eyJhb...",
  "token_name": "access_token"
}

For all later API requests, add the token as a cookie header: 

Cookie: access_token=eyJhb...

In Postman, add this value in the Headers tab with key Cookie and value access_token=eyJhb....

cURL Example

curl -X POST "http://<device-ip>:8080/api/crown/App/getModbusRegisters" ^
  -H "Accept: application/json" ^
  -H "Content-Type: application/json" ^
  -H "Cookie: access_token=eyJhb..." ^
  -d "{\"data\":{}}"

PowerShell Example

$headers = @{
  "Accept" = "application/json"
  "Content-Type" = "application/json"
  "Cookie" = "access_token=eyJhb..."
}

$body = @{
  data = @{}
} | ConvertTo-Json -Depth 5

Invoke-RestMethod `
  -Method Post `
  -Uri "http://<device-ip>:8080/api/crown/App/getModbusRegisters" `
  -Headers $headers `
  -Body $body `
  -TimeoutSec 60

Part 3 - Understand Request Format

Application CROWN APIs use the same URL pattern: 

POST http://<device-ip>:8080/api/crown/App/<api-name>

The request body has a top-level data object. Put function parameters inside this object. 

{
  "data": {
    "id": 1,
    "payload": "{\"refreshDuration\":1000}"
  }
}
Payload is a JSON string Many update and create APIs use a parameter named payload. In the request body, payload must be a text string that contains JSON. This is why quotation marks inside the payload are escaped as \".

A normal CROWN response has a header and a data section. If header.status is 0 and data.success is true, the API call succeeded. 

{
  "header": {
    "status": 0,
    "message": "Ok"
  },
  "data": {
    "data": "{\"id\":1,\"name\":\"S7 MDC\"}",
    "success": true,
    "message": "OK"
  }
}

For many APIs, data.data is also a JSON string. If your tool needs to inspect individual fields, parse that string once more.

Rule Meaning
HTTP methodUse POST for CROWN APIs. Use GET for the system health APIs.
API nameUse the function name from the manifest, but remove any leading underscore. Example: _readModbusRegister becomes readModbusRegister.
EventsManifest events are websocket topics. They are not listed as REST APIs in this manual.
NUM suffixFor advanced runtime APIs, replace NUM with the actual generated number, usually the IO-Link port number. Example: getIODDDefinitionsNUM can become getIODDDefinitions7.
TimeoutUse a timeout of at least 60 seconds.

Part 7 - Common Use Cases

Use Case 1 - Check Device Identity And Health

  1. Sign in and set the token cookie.
  2. Call GET /api/v1/system/info to confirm the correct device.
  3. Call GET /api/v1/system/monitor/stats to check CPU, memory, storage, and temperature.

Use Case 2 - Read Current App Configuration

Use this sequence before service work or before making changes. 

POST http://<device-ip>:8080/api/crown/App/getModbusServerInfo
{
  "data": {}
}
POST http://<device-ip>:8080/api/crown/App/getModbusRegisters
{
  "data": {}
}
POST http://<device-ip>:8080/api/crown/App/getIOLinkEndpoints
{
  "data": {}
}

Use Case 3 - Update One Endpoint Refresh Duration

This example changes endpoint 1 to a 1000 ms Sensor to Device polling interval. After the update succeeds, reload apps. 

POST http://<device-ip>:8080/api/crown/App/updateIOLinkEndpoint
{
  "data": {
    "id": 1,
    "payload": "{\"refreshDuration\":1000}"
  }
}

Typical response:

{
  "header": {
    "status": 0,
    "message": "Ok"
  },
  "data": {
    "data": "{\"id\":1,\"bitOffset\":16,\"enabled\":true,\"block\":4,\"accessTypeId\":1,\"bitLength\":32,\"name\":\"S7 MDC\",\"offset\":0,\"refreshDuration\":1000,\"portId\":7,\"targetId\":1,\"linkedModbusRegisterId\":1}",
    "success": true,
    "message": "OK"
  }
}
POST http://<device-ip>:8080/api/crown/App/reloadApps
{
  "data": {}
}
Device to Sensor timing For Device to Sensor endpoints used for Process Data OUT or ISDU read/write access, the polling cycle time is fixed at 5000 ms.

Use Case 4 - Create A Register And Link An IO-Link Endpoint

This sequence is useful when preparing a new mapping from an IO-Link value to a Modbus register.

  1. Check the required Modbus register quantity for the planned endpoint.
  2. Create the Modbus register with the required quantity.
  3. Create the IO-Link endpoint and link it to the register ID.
  4. Reload apps.
POST http://<device-ip>:8080/api/crown/App/getModbusQuantityForEndpointSource
{
  "data": {
    "portId": 7,
    "payload": "{\"targetId\":1,\"accessTypeId\":1,\"offset\":0,\"block\":4,\"registerTypeId\":2}"
  }
}
POST http://<device-ip>:8080/api/crown/App/createModbusRegister
{
  "data": {
    "payload": "{\"name\":\"S7 MDC\",\"registerTypeId\":2,\"dataTypeId\":1,\"startAddress\":0,\"registerQuantity\":2}"
  }
}
POST http://<device-ip>:8080/api/crown/App/createIOLinkEndpoint
{
  "data": {
    "payload": "{\"name\":\"S7 MDC\",\"portId\":7,\"targetId\":1,\"accessTypeId\":1,\"offset\":0,\"block\":4,\"refreshDuration\":1000,\"linkedModbusRegisterId\":1}"
  }
}
POST http://<device-ip>:8080/api/crown/App/reloadApps
{
  "data": {}
}

Use Case 5 - Change Modbus TCP Server Settings

This example enables the Modbus server on Ethernet interface P1. The API validation accepts port values from 500 to 600, max connections from 1 to 100, and transmit timeout from 0 to 3600000 ms. 

POST http://<device-ip>:8080/api/crown/App/updateModbusServerInfo
{
  "data": {
    "payload": "{\"port\":502,\"ethInterfaceId\":1,\"maxConnection\":10,\"transmitTimeout\":3000,\"enabled\":true}"
  }
}
POST http://<device-ip>:8080/api/crown/App/reloadApps
{
  "data": {}
}

Use Case 6 - Read And Write Runtime Values

Reading values is useful for commissioning checks. Writing values is only supported for Coil or Holding Register definitions, or through a configured Device to Sensor IO-Link endpoint. 

POST http://<device-ip>:8080/api/crown/App/readModbusRegisters
{
  "data": {
    "payload": "[{\"id\":1}]",
    "decodeHexValue": true
  }
}
POST http://<device-ip>:8080/api/crown/App/writeModbusRegisters
{
  "data": {
    "payload": "[{\"id\":1,\"value\":1234}]"
  }
}
POST http://<device-ip>:8080/api/crown/App/writeIOLinkEndpoint
{
  "data": {
    "id": 1,
    "payload": "{\"value\":1234,\"dataTypeId\":1}"
  }
}

Part 8 - Reload Apps After Changes

Saved configuration is not always active immediately in the running Modbus server and IO-Link polling processes. After using any API that changes configuration, reload apps when the change sequence is complete.

Change TypeReload Apps?
Update app settingsYes
Enable or disable an IO-Link portYes
Update Modbus server settingsYes
Create, update, delete, or reset Modbus registersYes
Create, update, delete, enable, disable, or reset IO-Link endpointsYes
Read device health, read configuration, or read current valuesNo
Write a runtime value through an existing register or endpointNormally no. Reload only if configuration was also changed.
 
POST http://<device-ip>:8080/api/crown/App/reloadApps
{
  "data": {}
}

Part 9 - Troubleshooting

SymptomLikely CauseRecommended Action
HTTP 401 or login page returnedMissing, expired, or wrong token cookie.Sign in again and send Cookie: access_token=<token> with the request.
header.status is not 0The platform rejected the CROWN call.Check the URL, API name, cookie, request method, and JSON body.
success is falseThe application rejected the request.Read message. Common messages include invalid_params, invalid_port_id, not_found_endpoint, and invalid_linked_modbus_register_quantity.
Request takes a long timeDevice is busy, the app is reloading, or IO-Link/Modbus work is heavy.Use at least a 60-second timeout and check /api/v1/system/monitor/stats.
IO-Link polling or Modbus values update slowly during API usageAPI requests are being sent too frequently for the available device hardware resources.Use APIs for remote configuration and service actions, not high-frequency data collection. Reduce request frequency and use Modbus TCP for regular process-data exchange.
Changed settings are saved but behavior did not changeRuntime processes are still using old configuration.Call reloadApps, wait for apps to restart, then read the configuration again.
Cannot link endpoint to registerRegister quantity is not exactly the required quantity, or the register is already linked.Call getModbusQuantityForEndpointSource, create a matching register, and confirm it is not linked to another endpoint.
Modbus value appears swapped in another systemThe client interprets bytes or words differently.Use big-endian bytes inside each register and high-word-first order for multi-register values.
